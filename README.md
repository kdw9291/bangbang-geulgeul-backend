# backend — Java 서버

아직 시작하지 않았다. `PROJECT_WORKFLOW.md`의 **S3 서버 연동** 단계에서 만든다.

## 확정된 것

- 언어는 **Java**. 앱 프레임워크(Flutter) 선택과 독립적이다.
- 저장할 데이터는 **긁은 긁기 단위 레코드 배열**이다. 마스크 픽셀을 저장하지 않으므로
  API가 단순해진다. 앱이 이미 쓰는 스키마(v1, 2026-08-14)는 이렇다.

  | 필드 | 뜻 |
  |---|---|
  | `scratchUnitId` | 긁기 단위 식별자 (불투명) |
  | `collectedAtUtc` | 수집 시각. **시간대가 반드시 붙는다** |
  | `utcOffsetMinutes` | **수집 당시** 기기의 UTC 오프셋 |
  | `memo` | 선택 입력 한 줄. 없으면 `null` |

  `utcOffsetMinutes` 를 따로 두는 이유는 **"수집 당시 사용자의 날짜"** 를 복원하기
  위해서다. UTC 만으로는 한국 8/15 00:30 수집이 다른 시간대에서 8/14 로 보인다.

- 식별자는 **`scratchUnitId`** 다. 앱의 `Region.scratchUnitId` 와 같은 값이며
  **불투명 ID 로 다룬다** — 값의 구조를 해석해 의미를 끌어내지 않는다.
  - 대부분은 통계청 시군구 코드(`sgg`)와 같다. 예: `47130` 경주시
  - **전부는 아니다.** 서울 `11000` · 제주 `50000` 은 통합으로 생긴 **합성 ID**,
    독도 `DK001` 은 신설 단위라 **통계청 네임스페이스 밖**이다.
    그래서 필드명을 `sgg` 로 두면 계약이 거짓이 된다
  - **자릿수도 계약이 아니다.** 지금 셋 다 5문자인 것은 우연이다
  - `000` 접미사로 통합 여부를 추론하지 않는다. 구분이 필요하면 명시적 필드를 도입한다
  - **ID 를 재사용하지 않는다.** 폐지된 단위의 ID 를 다른 단위에 다시 붙이면
    과거 기록이 엉뚱한 지역으로 옮겨간다
- 유효성 검증은 클라이언트가 보낸 값을 믿지 않고 **서버의 긁기 단위 카탈로그(현재 232개)에서
  조회**해서 한다. 알 수 없는 ID 의 처리 정책은 API 설계 시 정한다.
- **서버가 거부한 ID 를 클라이언트가 지우지 않는다.** 앱은 카탈로그에 없는 ID 도 보존하고
  표시에서만 제외한다(행정구역 개편·롤백 대비). 동기화는 전체 스냅샷 덮어쓰기가 아니라
  **ID 별 병합**이어야 한다.

## 아직 정하지 않은 것

- 프레임워크(Spring Boot 등), 빌드 도구, DB
- 인증 방식 — 계정 없이 기기 단위로 갈지, 소셜 로그인을 붙일지
- **`kind`(통합 단위 vs 시군구) 를 DTO 에 둘지.** 앱에는 아직 도입하지 않았다 —
  읽는 코드가 없어 선행 추상화이기 때문이다. 서버가 첫 소비자가 될 수 있다
- 행정구역 개편으로 ID 가 바뀔 때의 **마이그레이션 규칙**
- 저장소를 이 디렉토리에 둘지 별도 저장소로 분리할지

시작할 때 `AGENT_WORKFLOW.md`의 단계 승인 절차를 따른다. 먼저 Stage plan을
제시하고 승인을 받은 뒤 진행한다.
